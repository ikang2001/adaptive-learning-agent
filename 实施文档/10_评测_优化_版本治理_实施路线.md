# 评测、优化、版本治理与实施路线

## 1. 为什么这个项目必须有评测

如果只看：

> “LLM 输出挺合理”

项目会很虚。

必须建立可重复 benchmark。

---

# 2. 离线评测集

构造若干学生轨迹：

```text
StudentCase
├─ target_school
├─ current_progress
├─ availability
├─ attempts[]
├─ feedback[]
└─ expected_decisions
```

例如：

Case A：

```text
根轨迹表现稳定
耗时正常
→ 预期 NO_CHANGE
```

Case B：

```text
连续分离点错误
耗时翻倍
→ 预期 DEEP_DIAGNOSIS + REPLAN
```

# 5. 学习效率预测评测

核心：

```text
|predicted_duration - actual_duration|
```

可以看：

```text
MAE
MAPE
P50
P90
```

目标不是第一周就准，而是：

> 随着反馈积累误差下降。

---

# 6. 掌握度评测

可使用后续真实题表现验证：

```text
预测 mastery 高
→ 后续同知识点正确率是否高
```

关注 calibration，而不是只看一个分数。

---

# 7. 模拟卷评测

## 结构合规

- 总分；
- 题型；
- 考点比例；
- 难度；
- 题量。

## 题目质量

- 可解率；
- 答案正确率；
- 重复率；
- 知识点匹配率；
- 人工审核通过率。

## 个性化

- 是否覆盖学生真题薄弱点；
- 是否过度偏斜；
- 是否仍保持院校风格。

---

# 8. Regression Test

任何修改：

```text
Prompt
Model
Planner
Selector
Mastery
Harness
```

都必须跑固定 benchmark。

保存：

```text
baseline_result
candidate_result
delta
```

不允许“感觉新版本更聪明”就上线。

# 11. 优化优先级

推荐：

## P0：正确性

- 数据标签；
- 题目质量；
- 状态更新；
- 工具参数；
- 防幻觉。

## P1：稳定性

- retry；
- timeout；
- checkpoint；
- idempotency；
- trace。

## P2：效果

- mastery 算法；
- question ranking；
- replanning policy。

## P3：成本

- zero-token 分支；
- 小模型路由；
- cache；
- context compression。

不要反过来。

# 12. MVP → V4 实施路线

## MVP-0：数据骨架

实现：

- 知识树；
- 一个目标院校；
- 真题结构化；
- Question Pool；
- Student；
- Attempt。

验收：

能查：

```text
某学生某知识点最近题目表现
```

---

## MVP-1：计划闭环

实现：

- Student Model v1；
- 7 天计划；
- Daily Task；
- Feedback；
- Efficiency v1；
- Minor Adjust。

验收：

```text
提交反馈
→ 第二天题量发生合理调整
```

---

## MVP-2：Agent + Harness

实现：

- ToolRegistry；
- AgentLoop；
- State；
- Trace；
- Retry；
- Termination；
- 深度诊断；
- Major Replan。

验收：

正常反馈走确定性；
异常反馈进入 Agent；
执行路径不同。

---

## MVP-3：真题画像

实现：

- 真题任务；
- TrueExamErrorProfile；
- 阶段切换。

验收：

能回答：

```text
目标院校真题中，学生最薄弱的三个考点是什么？
```

---

## MVP-4：千人千卷

实现：

- ExamProfile；
- 专项卷；
- 全真卷；
- MockExam Validator；
- 模拟卷反馈。

验收：

卷子：

- 符合院校结构；
- 覆盖个人薄弱点；
- 无明显不可解题。

# 13. AI/Codex 开发约束

每个阶段开发时：

1. 先写接口和领域模型；
2. 再写测试；
3. 再实现；
4. 不跨层直接访问数据库；
5. 不让 Agent 直接修改核心状态；
6. 所有策略可替换；
7. 所有版本可追踪；
8. 重要 Tool 必须有单测；
9. Agent 修改必须跑 benchmark；
10. 每个 PR 写清楚：
   - 改什么；
   - 为什么；
   - 指标有没有变化；
   - 是否兼容旧数据。

# 15. 最重要的工程原则

项目未来可以换：

- 模型；
- Prompt；
- 掌握度算法；
- Planner；
- Question Selector；
- Mock Generator。

但不能轻易推倒：

- 领域模型；
- 事件历史；
- 题目 provenance；
- Agent trace；
- 策略版本记录。

这四个是后续持续优化的地基。
