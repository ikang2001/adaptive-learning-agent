# 自动控制原理「千人千案 + 千人千卷」智能复习 Agent 总体设计

## 0. 文档定位

本文档是项目的总纲，面向后续 AI/Codex/开发者实施。

项目参考“千人千案”的产品思想，但这里描述的是**我们自己的工程设计**，不声称商业产品内部采用相同技术实现。

项目只聚焦一门专业课：

> **自动控制原理**

核心目标不是“让 LLM 生成一份复习计划”，而是构建一个长期自适应学习系统，持续回答：

1. 这个学生现在最应该学什么？
2. 今天应该做哪些题、做多少？
3. 为什么安排这些内容？
4. 学生完成后表现如何？
5. 是否需要修改后续计划？
6. 什么时候进入目标院校真题阶段？
7. 真题做完以后，应该生成什么样的专项卷/模拟卷？

---

# 1. 项目一句话定位

基于 **Student Model × School Model × Question Model × Exam Model**，通过 Agent 动态执行诊断、选题、规划、Replan 与模拟卷生成，并通过真实学习反馈持续更新学生模型，实现自动控制原理专业课的：

- 千人千案：每个人复习内容、任务量、节奏不同；
- 千人千题：每个人练习题组合不同；
- 千人千卷：每个人冲刺阶段模拟卷不同。

---

# 2. 为什么不能做成普通“学习计划生成器”

普通方案：

```text
用户填写目标院校
    ↓
LLM
    ↓
输出 7 天计划
    ↓
结束
```

问题：

- 不知道学生到底哪里不会；
- 不知道同样 2 小时不同学生能完成多少任务；
- 不知道题应该刷什么，而不是只知道“刷根轨迹”；
- 不跟踪执行结果；
- 不会根据真实反馈动态修改；
- 真题做完之后没有持续学习闭环。

本项目必须形成：

```text
计划
 ↓
执行
 ↓
反馈
 ↓
诊断
 ↓
更新学生画像
 ↓
Replan
 ↓
下一轮计划
```

# 3. 四个核心业务模型

## 3.1 Student Model

回答：

> 这个学生现在是什么状态？

包含：

- 当前学习进度；
- 各知识点掌握度；
- 历史错题；
- 错误类型；
- 最近学习表现；
- 学习效率；
- 做题速度；
- 题目难度适应情况；
- 计划完成能力；
- 真题正确率；
- 模考表现；
- 当前复习阶段。

---

## 3.2 School Model

回答：

> 目标院校喜欢考什么？

包含：

- 院校；
- 专业；
- 科目代码；
- 自动控制原理考试范围；
- 历年真题；
- 知识点考频；
- 题型分布；
- 章节权重；
- 命题偏好；
- 难度分布；
- 历年变化趋势。

---

## 3.3 Question Model

回答：

> 这道题到底练什么？

每道题必须尽量结构化：

```text
Question
├─ id
├─ source
├─ school
├─ year
├─ chapter
├─ knowledge_points
├─ question_type
├─ difficulty
├─ score
├─ estimated_complexity
├─ solution
└─ provenance
```

核心原则：

> 不允许只按“章节”粗粒度刷题，必须尽可能细化到二级/三级考点。

---

## 3.4 Exam Model

回答：

> 一张“像这个学校出的卷子”的试卷应该长什么样？

包含：

- 总分；
- 考试时长；
- 大题数量；
- 题型比例；
- 章节比例；
- 高频考点；
- 难度比例；
- 常见考点组合；
- 真题年份权重；
- 命题风格约束。

# 4. 总体工作流程

```text
学生首次进入
    ↓
填写：
目标院校
当前复习进度
最近一段时间每天可用于专业课的时间
    ↓
加载 School Model
    ↓
建立初始 Student Model
    ↓
结合知识树计算当前优先级
    ↓
生成第一版 7 天计划
    ↓
Practice Planner 针对性选题
    ↓
学生学习
    ↓
反馈：
实际耗时
完成情况
正确率
错题
是否看答案
自评难度
    ↓
Agent 判断反馈是否异常
    ↓
正常：
轻量更新画像
    ↓
异常：
查询历史错题 / 讲义 / 真题
进行证据驱动诊断
    ↓
更新 Student Model
更新 Learning Efficiency
更新 Error Profile
    ↓
判断是否需要 Replan
    ↓
微调 / 重排计划
    ↓
继续学习
    ↓
进入目标院校历年真题阶段
    ↓
形成 TrueExamErrorProfile
    ↓
专项模拟卷 / 院校全真模拟卷
    ↓
模拟考试反馈
    ↓
再次更新 Student Model
    ↓
冲刺阶段动态规划
```

# 5. 计划时间的正确理解

系统不能假设：

```text
2 小时 = 所有人完成一样多的任务
```

学生提供的是：

> **可用学习时间上限**

系统实际安排任务时依赖：

```text
可用时间
    ×
历史学习效率
    ×
任务类型
    ×
题目难度
    ×
当前掌握度
```

第一周属于冷启动，效率估计可能不准。

随着学生反馈：

```text
任务预计 120min
实际 180min
```

系统逐渐修正该学生的效率画像。

# 6. 针对性刷题原则

错误方案：

```text
根轨迹薄弱
→ 刷 20 道根轨迹题
```

正确方案：

```text
根轨迹薄弱
↓
定位：
渐近线？
分离点？
出射角？
参数根轨迹？
综合绘制？
↓
根据目标院校考频
+
个人历史错题
+
当前掌握程度
+
题目难度
↓
生成针对性题目组合
```

例如：

```text
分离点基础题      4
分离点变式题      3
出射角基础题      3
根轨迹综合题      2
历史错题二刷      2
```

# 7. 真题阶段与“千人千卷”

学生完成目标院校历年真题后，系统形成：

```text
TrueExamErrorProfile
```

例如：

```text
稳态误差：真题正确率 45%
根轨迹分离点：38%
Bode 图：85%
系统校正：72%
```

之后支持：

## 7.1 专项模拟卷

目标：

> 解决特定知识漏洞。

允许显著提高薄弱考点占比。

---

## 7.2 院校全真模拟卷

必须同时满足：

1. 像目标院校；
2. 对该学生有针对性。

约束：

```text
目标院校真实题型结构
+
真实考点比例
+
真实难度分布
+
学生薄弱点适度加权
```

不能因为学生根轨迹弱，就生成 70% 根轨迹的“全真卷”。

---

# 8. Agent 的职责

Agent 负责：

> **动态决策，而不是所有业务计算。**

典型判断：

- 这次反馈是否异常？
- 是否需要深度诊断？
- 是否需要查询历史错题？
- 是否需要查讲义证据？
- 需要只微调明天，还是 Replan 整周？
- 继续专项训练还是进入真题？
- 真题完成后生成专项卷还是全真卷？
- 当前证据是否足够？
- 是否应该结束本轮分析？

---

# 9. Harness 的职责

Harness 是 Agent Runtime，不是业务逻辑本身。

必须至少具备：

- AgentLoop；
- ToolRegistry；
- StateManager；
- 参数校验；
- Timeout；
- Retry；
- Checkpoint；
- Guardrail；
- Termination；
- Trace；
- Audit；
- 模型/Prompt 版本记录；
- 工具调用结果持久化。

目标：

> 让 Agent 的动态执行过程可控、可恢复、可解释、可测试。

# 10. 确定性逻辑与 LLM 的边界

不能所有东西都交给 LLM。

## 适合确定性代码

- 日期计算；
- 剩余天数；
- 任务耗时统计；
- 正确率；
- 完成率；
- 历史速度统计；
- 题量约束；
- 考频统计；
- 基础优先级计算；
- 模拟卷题型比例校验；
- 最大 Agent 轮次；
- 权限与状态检查。

## 适合 LLM / Agent

- 错题原因语义分析；
- 薄弱点假设；
- 多证据冲突消解；
- 计划调整解释；
- 动态工具选择；
- 是否需要深入诊断；
- 模拟卷变式生成；
- 复杂复盘总结。

原则：

> LLM 负责语义和决策，程序负责事实、数值、约束和状态。

# 12. 可持续演进原则

后续优化必须遵守：

## 12.1 所有策略可版本化

例如：

```text
mastery_model_version
planner_version
question_selector_version
prompt_version
school_profile_version
exam_profile_version
```

避免模型升级后无法解释历史结果。

## 12.2 事件保留，不只保留最终状态

例如：

```text
TaskCompleted
QuestionAnswered
FeedbackSubmitted
MasteryUpdated
PlanReplanned
MockExamGenerated
```

这样未来可以重新计算画像。

## 12.3 核心策略配置化

不要把：

- 掌握度更新阈值；
- Replan 阈值；
- 最大 Agent 轮次；
- 题型权重；
- 难度比例；

写死在业务代码中。

## 12.4 所有 AI 结论必须可评测

后续新增能力前必须补：

- benchmark；
- regression test；
- online metric；
- trace。

---

# 14. 最终成功标准

不是“模型输出看起来很聪明”。

而是至少能够量化：

- 计划完成率是否提升；
- 预计耗时与实际耗时误差是否下降；
- 选题后目标知识点正确率是否提升；
- Replan 是否减少连续失败任务；
- Agent 不必要调用次数是否下降；
- 薄弱点诊断准确率；
- 真题正确率变化；
- 模拟卷结构合规率；
- 生成题可解率；
- 长期用户画像是否稳定。
